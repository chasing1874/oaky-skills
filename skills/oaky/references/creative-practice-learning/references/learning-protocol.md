# 方法与偏好学习协议

## 什么值得长期保存

一条规则通常应同时满足：

- 与当前用户的写作/创作、学习、工作目标、受众、品味、工具选择或已验证实践有关；
- 会改变未来至少一类任务中的判断，而不是只对本次输出有用；
- 能写成简洁、可执行、带适用范围的规则；
- 有明确来源，或由用户直接确认；
- 不需要复制大段原文也能成立。

资料中看起来精彩但尚未适配到用户的做法，先记为候选或实验，不直接写成确定规则。

## 文件选择

优先使用这些稳定文件：

- `references/positioning.md`：长期目标与定位，例如写作的服务对象和内容承诺、学习方向、工作角色与关注领域；
- `references/taste.md`：偏好与反偏好，例如表达、结构、视觉、节奏、学习方式和做事习惯；
- `references/experiments.md`：待验证的做法、实验结果、失败经验和规则状态。

内容积累后可以新建 Markdown reference：

- `references/platforms/<platform>.md`：只在特定平台或工具里成立的规则；
- `references/capabilities/<capability>.md`：可跨场景复用的能力，例如选题、结构、标题、封面、节奏、读书笔记、复盘或会议记录；
- `references/workflows/<workflow>.md`：属于用户本人、需要多步执行的稳定流程，例如每周复盘、资料整理或写作流程。

不要为了单条结论创建文件。先合并到最接近的稳定文件，达到一个清晰主题后再拆分。

## 规则格式

用自然 Markdown 表达，不强制复杂 schema。每条重要规则至少让读者看懂：

- 规则或判断；
- 适用范围；
- 当前状态：`候选`、`已确认`、`试验中`、`已验证` 或 `已停用`；
- 来源：报告、作品、资料名称或用户确认；
- 必要时记录反例、冲突或复核日期。

示例：

```markdown
## 开头先交代真实矛盾

- 规则：观点类文章优先从实际决策冲突切入，再解释方法。
- 适用范围：个人经验类和产品判断类写作；纯教程不强制。
- 状态：已验证。
- 来源：一次公开资料研究报告与用户确认。
- 反例：没有真实经历时，不编造冲突。
```

## 合并与冲突

1. 先读取目标文件，不凭记忆覆盖。
2. 同义规则合并，保留信息更完整且更具体的一条。
3. 新证据只适用于某个平台或内容类型时，缩小适用范围，不推翻全局规则。
4. 新旧结论冲突时保留冲突说明，并把旧规则标为待复核或已停用；不要静默删除历史判断。
5. 用户明确否定某条规则时，以用户当前判断为准，同时保留简短变更原因。
6. 更新发生版本冲突时重新读取最新版本，重新合并后再提交，不覆盖未见过的改动。

## 写入授权

以下表达可视为明确写入意图：记住这个方法或偏好、以后按这个来、更新我的方法与偏好（或我的创作方法）、把结论沉淀下来；或者用户在专门询问保存方式时直接选择沉淀到「我的方法与偏好」。普通的“挺有道理”“先看看”或对报告内容表示认可，不等于授权长期写入。

仅仅让你总结、分析、生成报告或参考某份资料，不等于授权长期写入。此时可以提出少量候选规则并询问是否沉淀；完整报告照常保存，不因用户暂不沉淀而删除。

写入前检查服务端返回的 capabilities。只有 `canEditContent=true` 才能更新；`canReset=true` 只表示可以恢复空模板，不代表可以删除该 Skill。

状态不要混用：

- 外部方法尚未由用户决定采用时为`候选`；
- 用户确认自己的定位、审美或反偏好时可记为`已确认`；
- 用户决定开始采用一个效果性方法，但本人结果尚未知时为`试验中`；
- 只有本人实践、复盘或事先约定指标提供支持后，效果性规则才是`已验证`。

## 执行工作流

1. 先判断用户是否明确表达长期写入意图，或是否在专门的保存问题中直接选择沉淀。没有则立即停止：不查询个人 Skill、不调用写入工具；最多提出候选规律并询问是否沉淀。
2. 用 `querySkills(action=list, scope=library)` 找到 `kind=personal_creative_practice` 的 Skill（产品名为「我的方法与偏好」或旧名「我的创作方法」）。
3. 用 `querySkills(action=get)` 获取当前版本和文件清单，只读取与本次结论有关的 reference 文件。
4. 判断输入是原始证据、一次性结论，还是值得长期复用的个人规则。证据不足时先提出候选结论，不直接固化为确定规则。
5. 把新结论合并到已有规则中：保留适用范围、证据强度、来源和验证状态；处理重复、冲突和过期规则。
6. 调用 `manageSkill(action=update)` 时必须携带刚读取到的 `expectedVersionId`，一次用户授权只执行一次写入。
7. 更新后简短说明改了哪个文件、增加或修订了什么，不把完整内部文件重复贴给用户。

## 边界

- 不把完整文章、逐字稿、作品、网页报告或对话流水写进 Skill。
- 不把所研究对象（作者、博主、他人）的人格、未经确认的身份推断或短期热点当作用户规则。
- 通用且完整的独立工作流应创建普通私有 Skill；只属于当前用户的适配结论进入「我的方法与偏好」。
- 称呼、沟通语气等每次对话都需要的少量全局信息，属于宿主或产品自身的记忆机制，不进入这里。
- 「我的方法与偏好」不可停用、卸载或归档；需要清空时使用专门的 reset 能力，不要尝试删除 Skill。
- 只修改服务端返回 `canEditContent=true` 的 Skill；市场和平台 Skill 始终按只读原件使用。
